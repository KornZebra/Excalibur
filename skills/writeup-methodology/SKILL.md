# CTF Writeup 撰写方法论

> 适用范围：writeup 仅用于 CTF 竞赛与授权环境记录。本方法论描述的是记录与复盘规范，
> 不包含也不得用于针对真实第三方目标的攻击编排。

## 一、六段式结构

一篇合格的 writeup 固定为六段，顺序不可省略：

1. **题目信息**：题目名、类别、分值、来源赛事、题干全文要点、附件清单与哈希（md5/sha256）。
2. **解题思路**：一句话点明突破口，再给判定链（看到 A 信号 → 推断 B → 验证方法 C）。
   这一节回答"为什么这样做"，是 writeup 的价值所在，不能只写"试了一下就出来了"。
3. **关键步骤**：可直接复现的命令与脚本，按执行顺序编号。每条命令标明作用与预期输出。
4. **flag**：完整 flag 原文，并注明提交是否通过、是否有大小写或格式要求。
5. **复盘与可迁移技巧**：本题用到的通用手法、绕过的坑、下次遇到同类题的捷径。
6. **时间线**：按时间戳列出关键动作与转折点，标出耗时最长的环节。

## 二、证据要求

- 每个结论后面必须跟证据：命令或工具 + 关键输出片段（截取决定性几行即可，不要整屏粘贴）。
- 脚本要贴最小可运行版本，路径、参数、依赖写清楚，保证他人复制即可复现。
- 涉及多阶段利用时，每个阶段给出中间产物（如泄露的地址、还原的明文、提取的文件名）。
- 用表格对齐"命令 → 输出 → 结论"三列，比大段文字更易核对。

## 三、如何避免写成流水账

- 不要按"我敲了什么"顺序写，而要按"证据链如何收敛"顺序写，失败的尝试折叠进复盘。
- 合并同类动作：同类目录爆破、同类 payload 试探归纳为一条方法论，只保留决定性的一次输出。
- 每节开头写一句本节目的，读者可以只读首句就理解结构。
- 删除无信息量的内容：重复的报错、无差异的响应、与结论无关的探索。

## 四、不确定性与失败尝试的价值

- 无法确定的部分要显式标注（如"libc 版本推测为 2.31，未在远程验证"），不要伪装成确定结论。
- 失败尝试是重要资产：记录"为什么这条路走不通"，能让后来者少走弯路。
- 区分"已证实""高置信推测""待验证猜想"三档，并给每档一个标记（如 ✅ / ⚠️ / ❓）。

## 五、提炼可迁移技巧

- 把题目特化解法抽象成模板：识别特征、适用条件、脚本骨架、常见变体。
- 记录工具参数组合与字典选择理由，而不只是命令本身。
- 归纳"信号 → 工具 → 攻击面"的对照表，形成自己的 checklist。
- 复盘时问三个问题：卡在哪里、当时缺什么信息、下次如何更早发现。

## 六、黑板与执行记录的组织

- 优先从黑板 facts（blackboard_list / blackboard_search）取已确认事实，避免凭记忆重写。
- 把黑板 facts 按"目标信息 / 服务与路径 / 凭据与令牌 / 中间产物"分组，再映射到六段式。
- 执行记录用于补充时间线，黑板用于保证结论一致性，两者冲突时以可复现验证为准。

## 七、交付前检查清单

- [ ] 六段齐全，flag 完整且已标注提交结果
- [ ] 每条结论都有命令与关键输出支撑
- [ ] 脚本可直接复现，路径与依赖完整
- [ ] 不确定项已标注置信度等级
- [ ] 失败尝试已折叠进复盘并给出原因
- [ ] 已提炼至少一条可迁移技巧
